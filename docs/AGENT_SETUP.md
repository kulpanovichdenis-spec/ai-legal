# Установка, настройка и выпуск с агентом

Передайте агенту с терминалом задачу: «Установи и настрой Legal AI Assistant по AGENTS.md. Запроси недостающие параметры, покажи изменения для утверждения, после подтверждения выполни согласованные push и deploy и проверь результат». Если агент не имеет прямого доступа к Git или серверу, администратор предоставляет разрешённый доступ либо выполняет соответствующий шаг по подготовленному плану.

Репозиторий исходного кода — [kulpanovichdenis-spec/ai-legal](https://github.com/kulpanovichdenis-spec/ai-legal). Администратор каждой установки выбирает свой компьютер или внутренний сервер и сообщает агенту разрешённый способ доступа. Для установки из утверждённого релиза достаточно прочитать репозиторий и развернуть его на выбранном сервере. Если администратор поручил изменить общий код и опубликовать изменения, отдельно выполни этап согласованного пуша в его репозиторий или форк.

## 1. Собери сведения

- Прочитай [README](../README.md), [границы безопасности](../SECURITY.md), [инструкцию запуска](QUICKSTART.md), [manifest](../backend/starter_content/manifest.json) и все перечисленные в нём файлы. Изучи существующие настройки экземпляра через админку или API, если он уже работает. Определи, какие правила применимы к организации, где остались демонстрационные записи и какие материалы понадобятся.
- Проверь `git status --short --branch`, наличие Docker и Compose, доступ к разрешённой среде, наличие действующего экземпляра, текущий релиз, состояние тома и прокси. Для нового экземпляра проверь свободный локальный порт. Команда `python ops/assistant_setup.py inventory` перечисляет все стартовые тексты и типовые маркеры заполнения. Проверь содержание вручную, поскольку маркеры покрывают только часть изменений.
- Составь один список вопросов, исключив всё, что уже известно. Секреты в вопросы и ответы чата не включай.

| Что выяснить | Что попросить у администратора |
| --- | --- |
| Контур и выпуск | Локальная проверка или внутренний сервер, целевой хост и каталог, если поручена публикация изменений — GitHub `owner/repo` и ветка для пуша, затем окно развёртывания и ответственный за проверку. Для существующей установки также способ резервирования и восстановления. |
| Модель и доступ | Внутренний API или разрешённый внешний провайдер, идентификатор модели, доступ из контейнера, способ ввода секретов, внутренний прокси и согласованный сетевой доступ. |
| Применимость текстов | Рабочие сценарии, юрисдикция, необходимость отраслевого чек-листа, контакт юридической службы и правила эскалации. Для инструкций, которые администратор хочет использовать, уточни владельца текста и наличие согласованной редакции. |
| Интеграции | Нужны ли задачи из веб-чата, входящий бот Bitrix24 или DaData. Для Bitrix24 уточни разрешённый портал, ответственного, политику передачи истории, маршрут вебхука и тестовую среду. Подтверждение перед созданием тестовой задачи получи отдельно. |
| Документы и формы | Для каждой позиции запроси точное название, действующую ссылку или файл, категорию, назначение, статус формы и связанные приложения. Отдельно уточни карточку реквизитов, комплект для контрагентов, список регламентов и допустимость передачи этих сведений модели. |
| Возврат и замена | Роль организации, категории товара, основания и исключения для каждого сценария, сроки, ответственных, канал передачи, минимальный набор сведений, названия и ссылки на утверждённые формы. При отсутствии утверждённого порядка оставь пример и зафиксируй вопрос как открытый. |

## 2. Подготовь и проверь экземпляр

1. По [инструкции запуска](QUICKSTART.md) подготовь новый `.env` из примера. Пароли и JWT-секрет сгенерируй локально. Ключ провайдера администратор задаёт через согласованное хранилище или защищённый ввод. Не выводи значения в чат, Git, команды с аргументами или общие журналы. Для уже настроенного экземпляра проверь параметры без печати значений и покажи план до изменения файла.
2. Начни с отдельного тестового экземпляра и синтетических данных. Проверь `docker compose config --quiet`, затем `docker compose up -d --build`, `docker compose ps` и HTTP-ответ от `/api/health`. Оставь loopback по умолчанию. Доступ сотрудников обеспечивается согласованным внутренним прокси. Из публичности репозитория доступ к экземпляру не следует.
3. Скопируй [пример профиля](../examples/instance-profile.json) и стартовые Markdown-карточки в закрытый каталог **вне Git**. Заполни карточки по ответам администратора. Добавь только согласованные инструкции, используя идентификаторы режима из manifest. Для каждого скилла укажи точное имя из manifest. Существующую карточку используй как основу, чтобы сохранить чужие правки. Не отправляй содержание рабочего профиля или документов в публичные системы. Для неуточнённых строк укажи, что они не настроены.
4. В профиле `modes` сопоставляет идентификатор режима с относительным путём к Markdown. `skills` сопоставляет название скилла с путём. Укажи только те записи, которые должны измениться. Инструмент сохраняет существующие настройки активации и сценарии, а при отсутствии стартового скилла использует его параметры из manifest. Он проверяет, что профиль находится вне репозитория.
5. Составь перечень документов для загрузки. Укажи файл, категорию и режимы. Сверь дубли с текущей библиотекой. Покажи администратору итоговый текст карточек через разрешённый внутренний канал, список файлов и экземпляр, куда они попадут. После подтверждения примени профиль и загрузи согласованные документы в админке. Настройка карточек не загружает файлы автоматически.

Команды для профиля работают на сервере либо через SSH-туннель до его loopback. При другом локальном порте передай `--url http://127.0.0.1:ПОРТ`. Python 3.10 или новее, дополнительные библиотеки не нужны. Пароль вводится без отображения либо задаётся оператором как секрет окружения `ASSISTANT_ADMIN_PASSWORD` на время процесса.

```sh
python ops/assistant_setup.py inventory
python ops/assistant_setup.py plan --profile /secure/assistant/profile.json
python ops/assistant_setup.py apply --profile /secure/assistant/profile.json --approved-plan PLAN_SHA256
python ops/assistant_setup.py plan --profile /secure/assistant/profile.json
```

`plan` читает настройки и показывает список изменений и контрольную сумму. Администратор подтверждает конкретные изменения, а агент подставляет полученную сумму. `apply` пересчитывает план и останавливается, если профиль или связанные настройки изменились. На время применения договорись об отсутствии параллельных изменений в админке. При сбое часть операций может быть уже сохранена. Повторно запусти `plan`, проверь остаток и получи подтверждение обновлённого плана. После применения повторный план должен показать ноль изменений.

## 3. Проверь сценарии

- Проверь вход администратора, наличие инструкций и скиллов, отображение документов и режимов. Убедись, что карточки сохранились после перезапуска.
- Выполни проверки из раздела [«Проверка на примере»](QUICKSTART.md#проверка-на-примере). Отдельно проверь консультацию, ссылку из каталога, поиск по синтетическому регламенту и два разных запроса о возврате и замене. Если ссылка или утверждённая процедура отсутствует, ответ должен это отражать. Проверь отсутствие автоматических публикаций и рабочий маршрут модели.
- Если администратор согласовал интеграции, примени [отдельные настройки](QUICKSTART.md#дополнительные-интеграции) и проверь их на тестовом портале после согласования внешней записи. Для OCR проверь распознавание на синтетическом скане. Для обезличивания используй вымышленные сведения.
- Зафиксируй результат каждого шага. При сетевой или модельной ошибке проверь статус контейнеров, доступ из backend и параметры модели. Не открывай порт и не подключай запасной внешний провайдер как обход без согласования.

## 4. Выполни согласованный Git push

1. В отдельном клоне или рабочей ветке подготовь только общие изменения. Настройки установки, `.env`, реальные ссылки, документы, дампы, логи и экспорт в Git не добавляй. Сверь точный список файлов через `git diff --cached --name-only` и проверь их содержимое. На первый публичный выпуск покажи лицензию и перечень файлов.
2. Покажи администратору изменения, имя репозитория, целевую ветку и назначение пуша. После подтверждения создай локальный коммит и выполни обычный пуш, например `git push -u origin HEAD:refs/heads/APPROVED_BRANCH`. Проверь URL `origin` перед пушем. Если репозиторий ещё не существует, его публичное создание согласуется вместе с публикацией.
3. Если ветка защищена, отправь согласованную ветку и действуй по правилам проверки проекта. Сверь опубликованный SHA. Для развёртывания используй только утверждённую ветку или релиз и зафиксированный SHA.

## 5. Выполни согласованный деплой

1. Покажи сервер, каталог, окружение, SHA, состав настроек экземпляра, окно работ, состояние данных, способ проверки и способ восстановления. Для существующей установки до обновления согласуй и проверь резервную копию базы и файлов. Зафиксируй предыдущий SHA и способ возврата. При незавершённых проверках доступа или резервирования оставь сервис на текущей версии.
2. После подтверждения подключись к указанному серверу. На новом экземпляре разверни утверждённый SHA в выделенном каталоге. В существующем клоне проверь локальные изменения и обновляй только согласованный checkout без перезаписи работы оператора. Приватный профиль и секреты доставляй отдельно по разрешённому каналу. Используй тот же Compose project и том для обновления.
3. Выполни `docker compose config --quiet` и `docker compose up -d --build`. Дождись здорового backend и рабочего входа, проверь `docker compose ps`, `/api/health`, модель, каталог и безопасный запрос по регламенту. Примени согласованный профиль к целевому экземпляру и подтверди результат чтением. Используй только предусмотренные прокси и сетевой доступ.
4. Если проверка провалилась, прекрати выпуск и покажи фактическое состояние. Восстановление выполняй по согласованному плану. Старый образ и прежняя база могут требовать совместимого восстановления, поэтому откат одного SHA после миграции следует проверить отдельно.
5. Сообщи администратору ссылку на репозиторий и ветку, развернутый SHA, внутренний адрес через согласованный канал, состояние данных и результаты проверок. Перечисли открытые вопросы, если часть профиля осталась демонстрационной.
