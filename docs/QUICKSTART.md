# Запуск и настройка

Для установки с агентом начните с [регламента установки агентом](AGENT_SETUP.md). Он использует команды ниже и добавляет согласование конфигурации, проверку перед пушем и контроль деплоя.

## 1. Подготовьте сервер

Нужны Docker Engine с Compose v2 или Docker Desktop. Первая сборка скачивает Python- и JavaScript-зависимости, модели поиска и компоненты OCR. Обеспечьте доступ к используемым реестрам и запас места под образы. Модель генерации разворачивается отдельно или предоставляется внешним провайдером.

Для первого запуска выберите локальный компьютер или внутренний сервер своей организации. Получите код и откройте терминал в каталоге проекта.

```sh
git clone https://github.com/kulpanovichdenis-spec/ai-legal.git
cd ai-legal
```

Скопируйте пример конфигурации в новый локальный `.env`.

```sh
cp .env.example .env
```

В PowerShell используйте `Copy-Item .env.example .env`. Если `.env` уже существует, откройте его и внесите нужные параметры.

## 2. Настройте пароли и модель

| Параметр | Что указать |
| --- | --- |
| `ADMIN_PASSWORD` | Отдельный случайный пароль первого администратора `admin`. |
| `DASHBOARD_PASSWORD` | Другой случайный пароль первого пользователя `dashboard`, даже если дашборд пока не используется. |
| `JWT_SECRET` | Третий независимый случайный секрет для подписи сессий. |
| `CORS_ORIGINS_STR` | При первом локальном запуске оставьте `http://127.0.0.1:8080`. Для согласованного внутреннего развёртывания укажите реальный origin браузера со схемой и портом, если он нестандартный. |
| `ALLOW_SELF_REGISTRATION` | Оставьте `false`. Этот флаг действует на регистрацию с паролем. Отдельный вход сотрудника по имени сохраняется. |
| `PUBLIC_PROJECTS_ENABLED` | Оставьте `false`. Значение `true` открывает просмотр опубликованных слайдов и имени автора без входа для всех, кому доступен экземпляр. |

Сгенерируйте три разных значения, например запустите `openssl rand -hex 24` три раза. В PowerShell 7 подойдёт `[Convert]::ToHexString([Security.Cryptography.RandomNumberGenerator]::GetBytes(24))`, также три отдельных вызова. Пароли из окружения задаются при создании записей в новой базе. Изменение файла после запуска само по себе их не меняет.

**Вариант А. OpenRouter**

```dotenv
OPENROUTER_MODEL=<доступный-идентификатор-provider/model>
OPENROUTER_API_KEY=<ваш-ключ>
INTERNAL_API_URL=
```

Выберите идентификатор модели, доступный вашему аккаунту. Для первой проверки используйте вымышленный текст. Ключ храните на сервере в `.env` с ограниченным доступом. Для чат-сценариев подходит модель с поддержкой потокового чата. Для автоопределения и вспомогательных запросов полезна стабильная выдача структурированного JSON.

**Вариант Б. Внутренняя модель**

```dotenv
OPENROUTER_MODEL=<установленное-имя:тег>
OPENROUTER_API_KEY=
INTERNAL_API_URL=http://llm.example.test:11434/v1
INTERNAL_API_KEY=ollama
```

Замените пример адресом, достижимым из backend-контейнера. Его `localhost` указывает на сам контейнер. Приложение добавляет к базе API путь `/chat/completions`. Укажите ключ, если внутренний сервер требует авторизацию. Имя должно содержать двоеточие и не содержать косую черту, чтобы приложение направило запрос во внутренний API.

Оставьте `MODEL_CONSULT`, `MODEL_AD_CHECK`, `MODEL_DOCUMENT_GEN`, `MODEL_REGULATION` и `ROUTER_MODEL` незаданными для использования базовой модели. При задании этих параметров идентификатор формата `provider/model` направляется в OpenRouter. Для проверки работы только с внутренним сервером оставьте внешний ключ пустым, не настраивайте внешние интеграции и ограничьте исходящую сеть на уровне инфраструктуры. Отдельно проверьте запросы маршрутизатора, переформулирования поиска и проверки ответа.

## 3. Запустите и войдите

```sh
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail 80 backend
```

Откройте `http://127.0.0.1:8080`. По адресу `http://127.0.0.1:8080/api/health` проверяется доступность API. Подключение модели и поиск проверяются отдельным запросом в чате. На странице входа выберите вкладку **Администратор**, введите `admin` и заданный пароль.

Для первичной работы на удалённом сервере с SSH можно открыть локальный туннель `ssh -L 8080:127.0.0.1:8080 user@internal-server`. Для доступа команды используйте согласованный внутренний прокси с TLS и сетевым ограничением. Вход по имени внутри приложения остаётся ограничением даже за прокси.

Данные хранятся в именованном томе Compose. `docker compose down` останавливает сервисы и сохраняет том. Флаг `--volumes` удаляет том вместе с базой, файлами и индексом. Перед обновлением и миграцией подготовьте согласованную резервную копию и проверьте восстановление на отдельном экземпляре.

## Документы и настройки

### Общая библиотека

1. Войдите как администратор и откройте **Документы**.
2. Выберите назначение. Для поиска используйте **Внутренний регламент** или **Справочный материал**. Для отраслевого источника есть **Листок-вкладыш**. Для скачивания готовой формы выберите **Шаблон документа**. Шаблоны доступны авторизованным пользователям и не индексируются как справочный текст.
3. Выберите режимы, где материал должен использоваться, и при необходимости добавьте описание. Можно выбрать до десяти файлов за раз с одинаковыми параметрами. Для документов с другим назначением создайте отдельную загрузку.
4. Проверьте результат по каждому файлу. Поддерживаются PDF, DOCX, DOC, TXT, MD, XLSX, XLS, JSONL, JPG, JPEG и PNG. Номинальный предел запроса на прокси — 30 МиБ, включая служебные части формы. Для сканов предусмотрено OCR, его качество зависит от изображения. Если загрузка завершилась ошибкой, проверьте список документов перед повтором: при сбое индекса запись могла уже сохраниться.
5. Откройте подходящий режим и задайте контрольный вопрос. Предупреждение о возможных персональных данных появляется после обработки и не блокирует загрузку. Проверьте состав файла до отправки на сервер.

### Вложение к одному чату

В чате используйте кнопку со скрепкой. Поддерживаются PDF, DOCX, DOC, TXT, MD, JPG, JPEG и PNG, до пяти файлов в интерфейсе. Такое вложение используется в контексте диалога, а извлечённый текст может сохраняться в базе вместе с диалогом. Для первой проверки берите синтетический файл.

### Инструкции и скиллы

- **Инструкции** задают основные правила режима. Начните с правил ответа и источников. Пример: «Сначала укажи, на какой внутренний документ опираешься. Если нужного правила в источниках нет, скажи об этом и предложи уточнить вопрос».
- **Скиллы** задают дополнительные правила для конкретного сценария. Например, создайте скилл «Согласование договоров», выберите «Поиск по регламентам» и добавьте короткую инструкцию в Markdown. Условия активации и приоритет позволяют точнее ограничить применение. Доступна также загрузка файла `.skill`.
- Для использования реквизитов или типовых форм сначала загрузите актуальные разрешённые материалы. Базовая конфигурация не включает документы организации.
- Изменения модели и интеграций в `.env` применяются после `docker compose up -d`. Изменения документов и инструкций через интерфейс хранятся в томе.

### Карточки, которые нужно заполнить

При первом запуске на чистом томе приложение копирует пять инструкций и девять скиллов в SQLite. Стартовые тексты лежат в [backend/starter_content](../backend/starter_content). Администратор правит рабочие тексты через **Инструкции** и **Скиллы**. Изменения сохраняются в томе и переживают перезапуск. При запуске поверх существующей базы её инструкции и скиллы сохраняются. Чтобы добавить в неё новые карточки, создайте их в интерфейсе и скопируйте текст из файлов ниже.

1. **[Каталог документов и типовых форм](../backend/starter_content/skills/document-catalog.md).** Замените демонстрационные строки. Для каждой записи укажите точное название, действующий URL или имя файла для скачивания, назначение, статус формы и связанные приложения. Для регламента загрузите текст отдельно в «Документах». Укажите владельца каталога и контакт юридической службы.
2. **[Возврат и замена товара потребителю](../backend/starter_content/skills/consumer-returns.md).** Укажите роль организации, категории товаров, основания и исключения, утверждённые сроки, список необходимых сведений, ответственное подразделение и канал передачи. Добавьте названия и ссылки на формы возврата, замены и обработки данных, если они применимы. Для файла из библиотеки укажите точное имя загруженного шаблона. Уберите неприменимые строки. Сохраните назначенные сценарии «Возврат товара» и «Претензия».
3. **Другие скиллы.** Сверьте чек-листы рекламы, формат документов, претензии и уведомления с правилами организации. В протоколе разногласий названия сторон заполняются по исходным данным. Для правил, которые зависят от регламента, добавьте источник в библиотеку. Используйте действующие названия карточек, чтобы ссылки на них в инструкциях и выбор скиллов оставались согласованными.
4. **Проверьте доступ.** Ссылка из каталога сохраняет права внешнего хранилища. Сам текст скилла может входить в запрос к модели. Вносите внутренние адреса и сведения только при разрешённой политике передачи данных.

Перед работой с реальными обращениями проверьте порядок возврата и замены на синтетических кейсах и согласуйте его с владельцем процесса. Если нужной записи или формы нет, ассистенту предписано сообщить об этом и запросить недостающие сведения.

## Дополнительные интеграции

Включайте только те интеграции, для которых согласованы сетевые маршруты и передача данных. Значения секретов храните в конфигурации целевого экземпляра.

### Создание задач в Bitrix24 из веб-чата

1. Подготовьте REST-вебхук Bitrix24 с правами на задачи и Диск. Укажите URL в `BITRIX24_WEBHOOK_URL` и ID ответственного в `BITRIX24_TASK_RESPONSIBLE_ID`.
2. При необходимости укажите `BITRIX24_TASK_ACCOMPLICE_IDS` через запятую и `BITRIX24_DISK_STORAGE_ID`. Пересоздайте контейнеры командой `docker compose up -d`.
3. В своём тестовом диалоге откройте создание задачи и проверьте заголовок, описание и историю, которая уйдёт вложением. После согласования проверьте назначение задачи и наличие вложения на тестовом портале. Ошибка загрузки на Диск может привести к созданию задачи без вложения.

### Входящие сообщения бота Bitrix24

Для канала бота нужны `BITRIX24_ENABLED=true`, `BITRIX24_BOT_ID`, REST-вебхук для отправки ответов и согласованный `BITRIX24_APPLICATION_TOKEN` или `BITRIX24_WEBHOOK_SECRET` для проверки входящих запросов. Стандартный Compose не проксирует `POST /bitrix/webhook` в backend. Если нужен бот, настройте маршрут отдельно в согласованном прокси, проверьте аутентификацию и исключите секреты из журналов прокси. Открывать остальные маршруты приложения для этой интеграции не требуется.

### Проверка контрагентов и распознавание

Для DaData задайте `DADATA_API_KEY` и `DADATA_SECRET_KEY` после согласования передачи идентификаторов. OCR входит в Docker-образ и запускается при обработке подходящего файла. Для дополнительного распознавания имён и организаций можно включить `ANONYMIZER_NER_ENABLED=true`, после чего проверьте качество маскирования на синтетическом документе. Подробности о данных, передаваемых модели, приведены в [SECURITY](../SECURITY.md).

## Проверка на примере

1. Загрузите [демонстрационный регламент](../examples/demo-contract-review.md) как **Внутренний регламент** для режима **Регламенты**.
2. В новом чате выберите **Регламенты** и спросите: «По демонстрационному регламенту кто согласует пилотный договор и сколько рабочих дней занимает первичная проверка?»
3. Сверьте ответ с документом. Ожидаемые ориентиры — координатор договоров и три рабочих дня.
4. Спросите, какой порядок предусмотрен для международных договоров. В примере такой порядок отсутствует.
5. Попробуйте приложить отдельный синтетический договор в режиме **Документы** и попросите выделить предмет, срок, цену и отсутствующие условия. Сверьте черновик с файлом.
6. Спросите ссылку на типовой договор поставки до заполнения каталога. Ожидаемый ответ — действующая ссылка пока не настроена. Затем добавьте разрешённую тестовую запись и проверьте, что ассистент возвращает точное название и этот адрес.
7. Задайте два синтетических вопроса по товару с недостатком, один о возврате, второй о замене. До заполнения карточки проверьте, что ответ уточняет исходные данные и направляет к владельцу процесса. После заполнения проверьте, что ответы различают два сценария и ссылаются на назначенные формы.

Если API отвечает, а чат выдаёт ошибку, проверьте идентификатор модели, ключ и сетевой доступ backend. Если чат работает без загруженного материала, проверьте категорию, режим, результат обработки файла и работу поиска. При проблеме с OCR повторите проверку на Markdown или текстовом PDF. При передаче диагностических журналов уберите секреты, адреса и содержимое пользовательских запросов.
